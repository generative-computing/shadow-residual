Shadow Residual with a shared LoRA A and per-intrinsic B

Status: complete. Shared-A vs vanilla SR on the 4 bench intrinsics: −0.65 / −0.50 / +0.36 / −1.37 pt (ans / guard / qc / req) for −33% params; see §5. Branch feature/different-arch. Owner: Claude session 3a884bc0. Last update: 2026-11-10.

1. The idea

Today every intrinsic adapter (answerability, guardian_core, query_clarification, requirement_check) is a separate SR adapter: per layer and per target module it owns a full LoRA pair (At, Bt). The idea under test:

Train one A matrix per (layer, module) that is shared by all 4 adapters, and give each adapter only its own ("proprietary") B matrix.

For a target module W (q_proj, o_proj, gate/up/down_proj, cross_stream) of task t:

vanilla SR   :  Δ_t(x) = (α/r) · B_t · A_t · x          A_t ∈ R^{r×in},  B_t ∈ R^{out×r}
shared-A SR  :  Δ_t(x) = (α/r) · B_t · A   · x          A shared across t ∈ {ans, guard, qc, req}

A is the "down-projection / feature extractor" (which r directions of the input to read); B is the "up-projection / writer" (what to do with them). Prior work found the two asymmetric: A matrices are largely task-agnostic input feature extractors while B carries the task-specific signal (Zhu et al. 2024, Asymmetry in Low-Rank Adapters of Foundation Models), and HydraLoRA (NeurIPS'24) shares one A across several B heads for multi-domain tuning. This experiment asks the question in the SR setting, on the four production intrinsics, with the adapter benchmark's own scorers.

What we hope to see

  • Accuracy: shared-A per-intrinsic accuracy within noise of (or above) vanilla SR. A could even help the small task (query_clarification, 2 153 rows) by borrowing features learned on the 3 large ones.
  • Parameters: 4 vanilla SR adapters = 4 × 60.95M = 243.8M trainable; shared-A = 40 layers × (A 671 744 + 4 × B 851 968) = 163.2M (−33%).
  • Serving: with a common A, a multi-intrinsic request computes z = A·x once per module and only the cheap B_t·z per intrinsic (the SR adapter stream is otherwise a second full forward per adapter; sharing A is the first step toward amortizing it).

2. Where it sits in SR

Every SR invariant is untouched: the base stream still runs base_layer only, K/V are base-only and shared, and with no adapter attached the model runs forward_bare. The change is entirely in how the LoRA deltas are parameterized and trained.

3. Training design

3.1 Joint multi-task training

A shared A has to be learned from all four tasks at once, so the four datasets are trained jointly in one job: the union of the 4 training sets, shuffled together, with every row tagged by its task id. Each row's LoRA deltas use the shared A and its own task's B (per-row routing inside a mixed batch). Bt therefore only receives gradient from task-t rows; A receives the sum of all four.

3.2 Implementation with stock PEFT (export = 4 ordinary SR adapters)

  1. Build the SR PEFT model as today (get_shadow_residual_peft_model) with adapter name answerability, then add_adapter the other three with the identical LoraConfig.
  2. Tie A: in every LoRA layer, lora_A[t] = lora_A[t0] — the same nn.Linear object under four adapter names. parameters() de-duplicates, so the optimizer and DDP see A once; state_dict() lists it under every adapter name, so per-adapter saving still works.
  3. Per-row routing (training only): each LoRA layer's forward is replaced on the instance by a routed version: 
    z     = A(dropout(x))                       # once, shared
delta = Σ_t  route[:, t] · (α/r) · B_t(z)        # route = one-hot task of each row
out   = base_layer(x) + delta
    The one-hot route is set by the trainer from the batch's task_ids just before the forward and read again on the gradient-checkpoint recompute (unchanged in between, so the recompute stays exact). All four Bt stay in the autograd graph every step (rows of other tasks multiply them by exactly 0), so DDP with find_unused_parameters=False works and absent tasks get an exact-zero gradient. Extra compute is 4× the B projection only (≈2% of a layer).
  4. Export: the trainer's ordinary save_model → PEFT save_pretrained writes every non-default adapter to out/<t>/adapter_config.json + adapter_model.safetensors — a completely stock SR adapter whose lora_A tensors are byte-identical across the four exports. Each loads with the standard path (build_sr_base + PeftModel.from_pretrained), so the benchmark's HF+PEFT reference code evaluates it with no change.

5. Results

Verdict. Sharing one A across the 4 intrinsics costs a small but real amount of accuracy: −0.5 to −1.4 pt on three intrinsics (two of them outside the 95% CI), ±0 on the smallest one, for 33% fewer trainable parameters across the family (163.2M vs 243.8M). The idea works as a compression trade-off, not as a free lunch: on these tasks A is not task-agnostic enough at r=32 to be shared without loss.

Sanity checks on the trained shared-A export

  • All 240 lora_A tensors are byte-identical across the 4 exported adapters (sharing held through DDP training and export); each export is a stock SR adapter (r=32, α=64, same 6 target modules, last_context_token=</think>) and loaded through the benchmark's unmodified hf_generate (which checks every saved weight was loaded).
  • Per-task B matrices are nearly orthogonal (mean cosine over the 240 B tensors 0.01–0.03), except guardian ↔ requirement_check: 0.15 — the two judge tasks that both answer {"score": "yes"|"no"} found partly shared write directions.
  • query_clarification's B has 2–3× the norm of the others' (1.39 vs 0.43–0.62): it receives ~2 000 Adam updates in the joint run vs 136 in its vanilla run (caveat in §6). It did not hurt its score (+0.36, n.s.).

Interpretation and next steps

  • The loss is largest on requirement_check and guardian, the two tasks whose B's overlap most — consistent with competition for the 32 shared input directions rather than with the Adam / step-count caveat (which affects the small qc task most, and qc is the one that did not lose).
  • The comparison confounds "A is shared" with "trained jointly in one mixed run" (2 376-step cosine schedule, Adam moving absent tasks' B). A joint run with A untied (same trainer, setup_shared_a without the tie) would split the two effects — the cheapest next run.
  • Cheapest ways to buy the accuracy back while keeping a saving: a larger shared rank (A r=64, B r=64: 4 tasks ≈ 40·(1.34M + 4·1.70M) = 326M — no longer smaller, so instead A r=48 / B r=48 ≈ 245M ≈ break-even; the saving shrinks quickly); or share A only on the cross_stream site, whose input h_base is identical for every task (the one place where sharing also amortizes compute at serving).
  • For the "add a 5th adapter cheaply" use case the result is encouraging: a frozen shared A plus a new B is a 34.1M-param adapter (56% of a full one) that, on this evidence, should land within ~1 pt of a full SR adapter.

6. Risks and design caveats

  • Adam on intermittently-present tasks. In a mixed batch of 32 the small task (qc, 5.7% of rows) is present in ~85% of optimizer steps. When it is absent its B gets an exact-zero gradient but AdamW still moves it (momentum, weight decay). Bqc also takes ~2 376 optimizer steps vs 136 in its vanilla run. This is inherent to joint training; it is the main reason qc might move either way.
  • Token-mean loss across tasks. The loss averages over supervised tokens of the batch. qc labels (clarifying questions, tens of tokens) outweigh 5–7-token labels of the other tasks per row; answerability is per-row the lightest. Same normalization as vanilla, but the tasks now compete for A.
  • Interference through A. A gets the summed gradient of 4 tasks; if their useful input subspaces differ, r=32 shared directions may be too few. A follow-up would be a larger shared rank (e.g. A r=64 with per-task B r=64, still fewer params than 4 vanilla).
  • Not a param-matched comparison per task: each exported shared-A adapter has the same shape (60.95M) as a vanilla one; the saving is across the family.
