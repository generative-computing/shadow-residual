1.1 What Shadow Residual is

Shadow Residual (SR) is a PEFT adapter that runs two parallel streams per decoder layer.

Each decoder layer runs:

  • A frozen base stream — bit-exact with the unadapted base model. Q/K/V/O/MLP use the base weights with no delta.
  • A trainable adapter stream — LoRA deltas plus a per-layer rank-R cross_stream injection drawn from the base stream.

Only norm(h_adapt) — the adapter stream's normed hidden state — reaches the LM head. Under the hood SR is an ordinary PEFT adapter; it just requires two custom PEFT module types (CrossStreamLora, ShadowResidualLora) and a dedicated loader.

Crucially, there is no architecture name in the config. Behavior is determined entirely by which fields are set. This deck documents the single training entry point, sr-train, and everything around it.

1.2 The class hierarchy — what inherits from what

Inheritance (vertical, gray) and containment (horizontal, blue). SR inherits directly from GraniteMoeHybridPreTrainedModel. The decoder layer holds attention, MLP projections (all _StreamGatedLinear), and a no-op CrossStream site. The dashed purple edges show the PEFT-time wrapping: CrossStream → CrossStreamLora (pure rank-R B·A, no base contribution) and each _StreamGatedLinear → ShadowResidualLora (stock PEFT LoRA plus a stream gate that turns the delta OFF whenever the layer computes under the frozen base stream).
SR needs these two custom wrappers because vanilla PEFT can't handle them: CrossStream has no weight to read shapes from (it's a no-op site), and the Q/K/V/O/MLP projections need a per-call gate so the LoRA delta never contaminates the frozen base stream. Both are registered via PEFT's LoraConfig._register_custom_module({type: wrapper}) in factory.py.

2.1 Data format & how it renders per model

Training data is JSONL, one chat conversation per row. The last message is the assistant's supervised target; optional documents carry the RAG context. The two model families render that context differently — the code handles the split automatically.

Raw data row INPUT (JSONL)

{
  "messages": [
    { "role": "user",      "content": "What is the capital city of France?" },
    { "role": "assistant", "content": "\"answerable\"" }
  ],
  "documents": [
    { "doc_id": "",
      "text": "The capital city of France is Paris. It is known for its iconic landmarks like the Eiffel Tower, Louvre Museum, and Notre-Dame Cathedral. The city has a population of over 2.2 million people." }

}

2.2 Handling the thinking / reasoning content

Granite 4.2 (ChatML) can emit a <think>…</think> reasoning block before its answer; Granite 4.1 has no such block. A single boolean — enable_thinking — controls whether that block is requested, and it flows through the same render_chat() helper on both the training and eval paths, so the two never drift. Below is the full lifecycle of thinking content.

The enable_thinking flag and the reasoning_content key

Two distinct things control thinking, and it helps to keep them apart:

  • enable_thinking carries no reasoning text. On Granite 4.2 it only shapes the trailing generation prompt (appended when add_generation_prompt=True): <think>\n when true (model generates its own reasoning) vs empty <think></think> when false. It does not affect how an already-present assistant message is laid out, and Granite 4.1 ignores it entirely.
  • reasoning_content (a field on the assistant message) is the only supported way to supply reasoning text on 4.2. If non-empty, the template wraps it as <think>\n{reasoning_content}\n</think>\n{content} — you provide plain text, the template adds the tags. Inlining <think>…</think> in content does not work: the generation prompt appends its own <think> opener, so a model trained that way emits a second block — you get two <think> sections.

The flag's value is forwarded through the shared render_chat() helper on both paths:

PathSource of enable_thinking (default False)
Training data.enable_thinking in the YAML, overridable by --thinking on sr-train (CLI wins).
Evaluation --enable-thinking flag on answerability_eval.
SR's loader passes messages through verbatim — it does not populate reasoning_content, so that key only takes effect if your JSONL rows already carry it. And keep training and eval in agreement: thinking is a prompt-rendering choice, so flip enable_thinking on for both sides or neither. The reference answerability adapters are trained thinking-off and evaluated without --enable-thinking.

Thinking in the training target

When thinking is off (the default), Granite 4.2's assistant turn still carries an empty reasoning block — the template emits <think></think> immediately before the label:

<|im_start|>assistant
<think></think>"answerable"<|im_end|>

The supervised label is the bare "answerable" that follows the empty tags (the <think></think> pair is part of the unmasked assistant turn the model is trained to reproduce). Granite 4.1 has no reasoning block, so its target is just "answerable". Response-only masking is unaffected either way: loss is computed on the final assistant turn regardless of whether it opens with an empty think block.

Thinking in generated output — the eval parser

At generation time a 4.2 model produces whatever the template shaped it for. If a non-empty reasoning block appears, the classifier must not mistake the reasoning prose for the label. process_predictions() in answerability_eval.py handles this by reading only the text after the last </think>:

pred = pred.strip()
# 4.2: the verdict is whatever follows the last </think>.
if "</think>" in pred:
    pred = pred.rsplit("</think>", 1)[1].strip()
# ... then take the first token / quoted word as the label
  • With a think block (e.g. <think>Okay, the user is asking…</think>"unanswerable") → everything up to and including </think> is discarded; the label is parsed from the remainder.
  • With an empty block (<think></think>"answerable") → the split leaves "answerable", parsed as normal.
  • No block at all (Granite 4.1) → the </think> branch is skipped; parsing is unchanged.
Set --max-new-tokens large enough to cover the reasoning block plus the label when thinking is on. The default (30) is sized for the thinking-off <think></think>"label" target; a real reasoning trace needs more room or it will be truncated before the label is emitted.

Training is driven by a single Pydantic-validated YAML. Behavior follows the fields you set — not an architecture name. Reference configs live in src/shadow_residual/config/. The only difference between a 4.1 and a 4.2 run is which config you point at (plus the base-model path); the code auto-adapts to each family's chat format and weight tying.

3.4 Modes of operation

There is no --mode flag. The mode emerges from two YAML fields: whether cross_stream is in target_modules, and whether invocation_tokens is set.

A

Plain LoRA — single-stream early-exit

cross_stream absent · invocation_tokens unset.

Dual-stream forward is skipped (early-exit path ≈ plain LoRA on Granite). shared_base_kv auto-resolves to false (K/V on the adapter stream; a warning is logged). Reference: lora-qkvo-mlp-r16.yaml.

B

aLoRA — gated activation

cross_stream absent · invocation_tokens set.

The delta stays off until the invocation token sequence appears in the input. Requires task_type="CAUSAL_LM" (schema sets it). Forces HF gradient_checkpointing off; train.py re-enables non-reentrant checkpointing explicitly. Reference: alora-all-linear-r16.yaml.

C

Shadow Residual (dual-stream)

cross_stream present in target_modules.

Dual-stream SR forward engages. shared_base_kv auto-resolves to true (one base-only K/V cache), which forbids LoRA on k_proj/v_proj. Optionally combine with invocation_tokens for gated SR. References: the sr-qo-mlp-*-sharedkv*.yaml configs.

The shared_base_kv auto rule: unset (null) means resolve from target_modules — true if cross_stream is present, else false. An explicit true/false always wins. Because it is not serialized into adapter_config.json, a checkpoint trained with a non-default value must pass the same value explicitly to the loader at serve time.

Also mode-shaping

  • param_dtype — fp32 master weights for 8B/30B stability vs bf16 throughout.
  • runtime.fsdp + accelerate launch — DDP vs FSDP sharding; drives the FSDP-aware post-training generate path.
  • Response-only masking — auto: TRL assistant_only_loss=True when the chat template has {% generation %} markers, else the hand-rolled ResponseOnlyCollator (masks everything before the last assistant marker).

Part 4

Advanced details

Deeper mechanics for the curious: how the dual-stream architecture is glued to PEFT, how it collapses to plain LoRA when cross-stream is off, how the K/V regimes and aLoRA gating work, and how it all scales under FSDP.

4.1 Why Wcross is a no-op in the base model

The per-layer cross-stream edge is h_adapt += B(A · h_base) — a rank-R projection from the base stream into the adapter stream. But in the base model the cross_stream site is a zero-output nn.Module with no parameters at all:

class CrossStream(nn.Module):
    """No-op site that PEFT can wrap with a CrossStreamLora layer."""
    def __init__(self, hidden_size):
        self.in_features = self.out_features = hidden_size
        self.register_buffer("_device_anchor", torch.zeros(1), persistent=False)
    @property
    def weight(self): return self._device_anchor
    def forward(self, h_base, *a, **k): return torch.zeros_like(h_base)

The decoder calls h_adapt = h_adapt + self.cross_stream(h_base), which adds zero until PEFT installs a CrossStreamLora in its place. The rank-R A / B weights live on the installed adapter, not on the base module. Two reasons it has to be a real module rather than nothing:

  • It's a targetable site. PEFT's LoraModel discovers what to wrap by walking named child modules and matching target_modules. Listing "cross_stream" only works if there is a child module by that name to find and replace. There is no nn.Linear in the SR decoder whose (input, output) is (h_base, h_adapt) — the two streams are independent accumulators, so PEFT's "intercept an existing linear" rule can't synthesize the edge. The no-op site is what gives PEFT something to replace.
  • The device anchor. peft…_replace_module calls next(child.parameters()) to find a device for the new adapter weights. A truly empty module raises StopIteration. The one-element _device_anchor buffer (and the weight property) satisfy PEFT's introspection without adding any trainable parameter.
Cross-stream is the only base→adapter coupling within a layer. Everything else keeps the two streams parallel and independent. That is why the wrapped/unwrapped state of cross_stream is the right runtime signal for whether the dual-stream forward is worth running at all (§4.3).

4.2 The PEFT implementation — two custom wrappers

Vanilla PEFT only knows how to wrap nn.Linear-shaped modules and always applies the delta. SR needs two things PEFT can't provide out of the box, so it registers two custom module types via LoraConfig._register_custom_module({type: wrapper}) in factory.py:

Target typeWrapperWhat it adds
CrossStream CrossStreamLora Implements LoraLayer directly. Owns rank-R lora_A/lora_B ModuleDicts (A ← Kaiming, B ← 0, so the edge starts at exactly zero). forward(x) = 0 + Σ B(A(x))·scaling — the base layer contributes nothing. merge/unmerge are no-ops (no base weight to fold into).
_StreamGatedLinear ShadowResidualLora Subclasses stock peft.tuners.lora.Linear. Adds a one-line gate at the top of forward: if current_stream() == "base" → return base_layer(x) (delta OFF); else delegate to stock PEFT (delta ON, with any variants like aLoRA/DoRA). Inherits everything else for free.

The stream gate is the whole trick behind the frozen-base guarantee:

def forward(self, x, *args, **kwargs):
    if current_stream() != "base":
        return super().forward(x, *args, **kwargs)   # stock peft: base + LoRA delta
    kwargs.pop("alora_offsets", None)
    kwargs.pop("adapter_names", None)
    return self.base_layer(x, *args, **kwargs)        # frozen-base path: no delta

Every Q/K/V/O/MLP projection is a _StreamGatedLinear (a marker subclass of nn.Linear, behaviourally identical). The marker subclass is the dispatch key: PEFT matches on exact type(module), so only the SR decoder's projections get the stream-gated wrapper — not the lm_head or unrelated linears.

Why a marker subclass, not nn.Linear directly? If SR targeted plain nn.Linear, PEFT would also wrap the lm_head and any other linear in the graph. The distinct _StreamGatedLinear type lets the registry select exactly the decoder projections that need the per-call stream gate.

4.3 The adapter-only early-exit

The base model is always ShadowResidualForCausalLM — construction never branches on whether cross-stream is configured. Instead the forward branches at runtime. At the top of the decoder loop the model asks _any_cross_stream_wrapped(self.layers): is any cross_stream site an installed CrossStreamLora (vs. a bare CrossStream)?

cross_stream_active = _any_cross_stream_wrapped(self.layers)
if cross_stream_active or shared_base_kv:
    #  → dual-stream path: maintain (h_base, h_adapt)
else:
    #  → adapter-only early-exit: only h_adapt

When neither condition holds, the early-exit collapses the layer to a single stream. What gets skipped: the base Q/K/V/O pass, the base MLP, the cross_stream(h_base) call, the cat([h_base, h_adapt]) layernorm fusion, and the h_base initialization. What still runs: one Q/K/V/O/MLP pass on h_adapt with every LoRA delta firing, and aLoRA gating via PEFT's hook. Result: compute equal to plain LoRA on Granite — no dual-stream surcharge — which is exactly what you want when training LoRA/aLoRA without cross-stream.

Note the or shared_base_kv. Shared-base-K/V mode also takes the dual-stream branch even with no cross-stream wrapper installed (the "weak SR" ablation). The gate is "cross-stream active or shared K/V requested", not cross-stream alone.
The gate is only meaningful after get_peft_model. "Is this CrossStream wrapped?" is only true once PEFT has installed its wrappers. Forwarding the bare SR base before get_peft_model always takes the early-exit path.

4.4 Disjoint vs shared-base K/V

Within the dual-stream forward there are two ways to handle attention keys/values, selected by config.shared_base_kv. Both keep the base trunk's attention reads adapter-free; they differ in how many K/V projections and caches exist per layer.

Disjoint K/V shared_base_kv=false

Each stream computes its own K and V. Two K/V projection calls per layer, two physically separate caches:

  • past_key_values_base — Wkv·normed_base, computed under stream_context("base") (delta gated off), read by the base attention.
  • past_key_values — computed under "adapter" on normed_adapt (K/V LoRA delta may fire), read by the adapter attention.

K/V LoRA on the adapter is allowed; it never leaks into the base reads because the caches are disjoint.

Shared-base K/V shared_base_kv=true

K and V are computed once, under "base" from normed_base (frozen). Both streams' queries attend that single K/V:

  • The adapter stream computes only Q (Q LoRA fires) and O; it does not compute its own K/V.
  • Only past_key_values is written; past_key_values_base is unused.
  • K/V LoRA is structurally forbidden — _reject_kv_lora_when_shared raises at build time if k_proj/v_proj appear in target_modules.

The payoff: the adapter can attend over a KV cache populated by the frozen base, so keys/values need not be recomputed when the adapter turns on.

Which is the default? config.shared_base_kv is false at the model level, but the training layer resolves an unset (null) YAML value to true when cross_stream is present — the SR production default — and false otherwise. It is not serialized into adapter_config.json, so a checkpoint trained with a non-default value must pass the same value explicitly at load time (see §3.4).

4.5 aLoRA gating (FASO-style mid-sequence activation)

SR-PEFT is aLoRA-class: the adapter contributes nothing on tokens before an activation marker, and the full delta at and after it. This is how the adapter can be "invoked" partway through a sequence (e.g. only for the assistant's answerability verdict) while the prompt tokens stay bit-identical to the base model — the property that makes the base KV cache reusable.

The mechanism is almost entirely stock PEFT. Set LoraConfig.alora_invocation_tokens=[ids…] (with task_type="CAUSAL_LM") and:

  1. PEFT auto-attaches ALoraLinearVariant to every wrapped projection.
  2. A pre-forward hook on every LoraLayer scans input_ids, finds the rightmost match of the invocation sequence, and computes per-row alora_offsets = number of trailing positions at/after the match.
  3. The variant builds mask = pos ≥ (T − offset) and only runs the LoRA matmul on the post-marker rows — the delta arithmetic itself is gated, not just zeroed afterward.

CrossStreamLora participates in the same flow: because it inherits LoraLayer, it receives alora_offsets from the same hook and masks its rank-R contribution to the trailing positions, mirroring ALoraLinearVariant. The SR decoder itself computes no mask and threads no activation kwarg — PEFT drives gating end-to-end, and alora_invocation_tokens round-trips through adapter_config.json.

The three-knob rule. aLoRA gating fires only if all three are set: alora_invocation_tokens, task_type="CAUSAL_LM", and (for gated SR) "cross_stream" in target_modules. Miss any one and PEFT silently falls back to unconditional LoRA — no error. The invariant tests (test_alora_invocation_invariant.py) pin the pre-invocation logits/KV equality; the task_type requirement was discovered by those tests.

4.6 The fused→unfused weight transfer

Upstream GraniteMoeHybridForCausalLM stores the MLP gate/up as a single fused shared_mlp.input_linear. SR uses unfused per-projection tensors so PEFT can attach a separate LoRA to each. transfer_base_weights(src, dst) slices the fused weights into the SR layout:

shared_mlp.input_linear.weight  [2I, H]  →  gate_proj.weight  [I, H]
                                            up_proj.weight    [I, H]
shared_mlp.output_linear.weight          →  down_proj.weight
q_proj / k_proj / v_proj / o_proj        →  copied as-is (already unfused upstream)

The copy is torch.no_grad().copy_ into pre-allocated destination tensors, so shapes must match exactly (a mismatch is a hard fail). Numerics are not bit-identical to a fused forward because the reduction order changes (two separate matmuls vs one) — a documented divergence, and the reason "plain LoRA on the SR base" is functionally but not bit-wise equal to LoRA on stock Granite.

4.7 FSDP & post-training generation

8B and larger runs shard with FSDP (via accelerate launch + the shipped fsdp_4gpu.yaml). Two SR-specific concerns:

Untied lm_head is FSDP-safe

Granite 4.1 ties lm_head to embed_tokens; Granite 4.2 ships a separate trained lm_head.weight. SR settles the tie decision in the model's __init__ from config.tie_word_embeddings — which runs on every rank (including meta init) before the FSDP wrap. So the parameter structure is identical across ranks when FSDP flattens, and there is no divergence. Only when tied does SR register _tied_weights_keys = {"lm_head.weight": "model.embed_tokens.weight"}.

Post-training generation under FSDP

After training, train.py can generate against the in-memory model. Under FSDP the model is sharded, so run_generation_under_fsdp does a careful gather/rebuild (verified at 30B on 4×80GB H100):

  1. All ranks gather a FULL_STATE_DICT (rank0_only=True, offload_to_cpu=True).
  2. All ranks null every caller-side reference to the FSDP module (release_model_refs() — e.g. trainer.model). This is load-bearing: the ~16GB flat-param shard stays pinned otherwise and the rebuild OOMs.
  3. All ranks accelerator.free_memory() (drops the ~29GB reserved arena) + del + gc + empty_cache → rank 0 returns to ~0GB.
  4. Rank 0 only rebuilds a fresh non-FSDP SR+PEFT model (meta init) → load_state_dict → .to("cuda:0") → run_generation.
Two escape hatches for scale. Use --skip-post-train-generate to run generation as a separate process against the saved checkpoint — a fresh CUDA context sidesteps the post-training residue that OOMs the in-process gather+rebuild at 30B. And the FSDP save must consolidate (fsdp_state_dict_type: FULL_STATE_DICT): with SHARDED_STATE_DICT, save_model writes .distcp shards and no adapter_model.safetensors, which loads as nothing. train.py fails loudly on rank 0 if the consolidated adapter files are missing.

4.8 Why merge_and_unload is disabled

Standard PEFT lets you fold the LoRA delta into the base weight (merge_and_unload). SR monkey-patches it to raise NotImplementedError (factory.py:_disable_merge_and_unload), on both the returned model and its base_model. Folding W + ΔW into the base linear would silently contaminate the frozen base stream: the next stream_context("base") call would return (W + ΔW)x instead of Wx, breaking the invariant the whole architecture exists to guarantee. Save/load is unaffected — it goes through the state-dict path (save_pretrained / load_shadow_residual_peft_model), not merge.
