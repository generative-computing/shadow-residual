SR adapters as tools

Exposing a Shadow Residual answerability adapter to Granite 4.2 through the model's native tool-invocation capability — the <tool_call> becomes the switch trigger, and the adapter generates the <tool_response> verdict plus the user-facing answer.

Some of the “tools” registered with the model are really SR adapters. When the base decides to call one — e.g. the standard answerability adapter — the switch runtime intercepts right after the model emits its <tool_call>, before an end-of-text token is produced, flips generation to the adapter, and the adapter produces a real response under stock generate().

The switching mechanism itself is out of scope here. This document covers the training bootstrap: what the adapter must learn to emit, how the data is shaped, where the supervised boundary falls, how it wires into the shadow-residual pipeline, and how it compares against the plain answerability flow.

1 · The goal

Granite's native tool-calling is reused as a switching trigger. The target base is Granite 4.2 (ChatML template, <|im_start|> / <|im_end|>, <tool_call> / <tool_response> tags).

Design decision. After </tool_call> the adapter generates the <tool_response> verdict block and the opener of the next assistant turn (<|im_start|>assistant\n), then stops. It emits the structural scaffolding and the handoff point but not the user-facing answer — the base (or another adapter) generates that, which is out of scope here. The switch does nothing but route tokens to the adapter; it does not synthesize the tool result.

2 · What the adapter emits

The adapter starts right after the base's </tool_call> and emits the two-part span below. Note it reproduces the <tool_response> as a user-role turn — that is how 4.2 natively represents retrieved/tool context.

<|im_start|>user
<tool_response>
{"answerable": true, "rationale": "The HR handbook states 16 weeks of paid parental leave is available to all parents regardless of gender, which covers new fathers."}
</tool_response>
<|im_start|>assistant
<think></think>Yes. New fathers are eligible for 16 weeks of paid parental leave, which can be taken any time within the first 12 months after your child's birth or adoption. The policy applies to all parents regardless of gender or caregiver role.<|im_end|>

3 · The token boundary

What the base model generates for the answerability tool-call turn (verified by diffing the add_generation_prompt=True prefix against the rendered call turn):

\n<tool_call>\n<function=answerability>\n<parameter=question>\n…\n</parameter>\n</function>\n</tool_call>\n<|im_end|>\n

The base's turn naturally ends with </tool_call>\n followed by <|im_end|>, which is the stop token. If the base emits it, generation halts and the adapter never runs. Therefore the switch must intercept at </tool_call> — before <|im_end|> is committed — parse the emitted tool_call, see that it names an SR adapter, and flip generation to that adapter.

The last context token is </tool_call>. The adapter owns <|im_end|> onward.
On <tool_call> vs. tool_calls. The literal <tool_call><function=…> tags exist only in the rendered template string. In the message object a tool call is the structured tool_calls key; the chat template materializes it into the tags, and an inference-time parser does the inverse (</tool_call> text → tool_calls object). Training rows store tool_calls as structured objects, never as literal tag text.

4 · The single-<|im_end|> design

This is the load-bearing constraint of the whole bootstrap.

<|im_end|> is the generation stop token. The switch calls a stock generate() with default EOS handling and no custom stopping criterion, so the decode loop halts at the first <|im_end|> the adapter produces. A faithful ChatML stream would contain a second <|im_end|> closing the <tool_response> turn before the answer turn — but emitting that would stop generation prematurely, before the answer.

So the intermediate turn-closing <|im_end|> is dropped: the adapter flows directly from </tool_response>\n into <|im_start|>assistant, and the single <|im_end|> at the end of the answer is its genuine, first-and-only stop.

Single-<|im_end|> (shipped)

  • Exactly one <|im_end|>, at the very end.
  • Slightly off-spec ChatML: the <tool_response> turn is not closed before the assistant turn opens.
  • Harmless if nothing re-parses the output as structured turns; the explicit <|im_start|>assistant still marks the boundary.
  • Structural validity: 0 → 1.0 once adopted.

Fully-stock ChatML (rejected default)

  • Places an <|im_end|> after </tool_response>.
  • Under stock generate() the adapter emitted \n<|im_end|> and halted immediately — never reached the answer.
  • Only viable if the switch owns the decode loop with a stopping criterion that ignores the first N−1 stops — out of scope.
Shipped as single-<|im_end|> in the data. The generator emits pre-rendered {"text"} rows with exactly one, terminal <|im_end|> — the intermediate turn-closer is omitted in the training data itself, not just worked around at inference. Verified byte-identical to the stock 4.2 template except for the two omitted <|im_end|> seams. Boundary verified on real data: token before supervision = </tool_call>; supervised span = the <tool_response> verdict + answer, ending at the single terminal <|im_end|>.

The --thinking flag (3 modes)

What the answer turn emits right after <|im_start|>assistant\n is controlled by make_tool_adapter_data.py --thinking. The tool_response block and template scaffolding are built identically through the assistant opener in all three modes; only the think prefix differs. Because the collator cuts at </tool_call>, the prefix is part of the supervised span — the adapter learns to emit it.

ModeAfter assistant\nNote
off (default)"answerable"<|im_end|>No think block; shortest completion.
enabled<think>"answerable"<|im_end|>Open think tag; adapter reasons before the verdict.

5 · Two formatting modes: autoregressive vs. external

Sections 2–4 describe autoregressive_tool_formatting, the original design: the adapter owns everything after the base's </tool_call>, including the ChatML scaffolding. external_tool_formatting, now the default, takes the opposite stance: the serving environment owns the template and the adapter only produces the tool's payload. It became the default after the full-scale Vela run (0.9541 verdict accuracy, 100% structurally valid; §11). Pass --tool-formatting autoregressive_tool_formatting to the generator and the trainer for the original mode.

autoregressive_tool_formatting

  • Adapter starts after the base's </tool_call>.
  • Adapter emits <|im_start|>user\n<tool_response>\n{dict}\n</tool_response>\n<|im_start|>assistant\n[think]answer<|im_end|>.
  • One generate() call covers three logical turns; the runtime is trivial but has to re-segment the output (§10).
  • Markers: assistant_marker = last_context_token = </tool_call>.
  • --thinking applies (answer-turn think prefix).

default external_tool_formatting

  • Env writes \n<|im_end|>\n<|im_start|>user\n<tool_response>\n (closing the base's turn, opening the tool turn) and hands over.
  • Adapter emits only {"answerable": true}, then stops on EOS (<|im_end|>).
  • Env drops the EOS and appends \n</tool_response>\n<|im_end|>\n; the base then writes the final answer itself.
  • Markers: assistant_marker = <tool_response>\n, last_context_token = \n.
  • No answer turn, so --thinking does not apply.

The external span, token by token

[M] …</function>\n</tool_call>           ← base
[M] \n<|im_end|>\n<|im_start|>user\n         ← env (stock template glue)
[M] <tool_response>\n                         ← env; last context token = "\n"
    >>> MASK BOUNDARY (right after <tool_response>\n) <<<
[S] {"answerable": true}                      ← adapter
[S] <|im_end|>                                 ← adapter's stop (EOS); env discards it
    \n</tool_response>\n<|im_end|>\n            ← env appends; base resumes
Why the trained span ends in <|im_end|>, not \n</tool_response>. Under stock generate() the only stop is EOS. If the adapter learned to emit \n</tool_response> it would run on into whatever comes next. Training it to emit the dict and then <|im_end|> gives a clean, engine-native stop. The environment treats that EOS as “payload done” and writes the closing tag itself. </tool_response> is a single special token (id 100273), so an env that prefers it can also use it as a stop string.
Verified against the stock 4.2 template. An external row with the env suffix appended is byte-identical to apply_chat_template([…, assistant(tool_calls), tool(dict)]), so the transcript the base re-reads is fully stock ChatML with no off-spec seams (unlike autoregressive mode). The external context is the autoregressive context plus the stock glue, so the two modes see identical prompts up to </tool_call>. Both are covered by tests/training/test_tool_formatting.py: template identity, the collator supervising exactly {dict}<|im_end|>, and the boundary validator.

Enabling it

# data (one row per adapter call; external is the generator default, --thinking must stay off)
python scripts/make_tool_adapter_data.py --input <answerability.jsonl> --base-model <4.2> \
  --out-train train.jsonl --out-val val.jsonl

# train (the config defaults to external; no mode flag needed)
sr-train --config src/shadow_residual/config/sr-tool-adapter-answerability-g42.yaml \
  --train-data train.jsonl --val-data val.jsonl …

# eval (mode read from each row's metadata.tool_formatting)
python scripts/eval_tool_adapter.py --base-model <4.2> --adapter <ckpt> --val val.jsonl

In external mode the eval cuts the prompt at <tool_response>\n and requires the entire generation (up to EOS) to parse as a dict with a boolean answerable. It reports structural_rate, verdict_accuracy, a confusion table, and eos_stop_rate (the fraction that ended on EOS rather than hitting max_new_tokens).

Tool logic is opt-in for the whole repo. data.tool_formatting defaults to unset: standard chat SFT, rows must carry messages, and pre-rendered {"text"} rows are rejected. Setting the field (YAML) or passing --tool-formatting [MODE] (a bare flag means external) enables the passthrough and fixes the three boundary markers per mode. The mode is recorded into adapter_config.json.

6 · Training-data construction

Each training row is a full conversation ({"messages": […], "tools": […]}) rendered with apply_chat_template(…, tools=…, add_generation_prompt=False, enable_thinking=False) — exactly the shape data.py already consumes.

The generator takes answerability-style rows (question + documents + gold verdict) and emits the agentic conversation shape, one row per adapter tool-call. The example RAG flow — search_kb → answerability (answerable) → answer → follow-up → answerability (unanswerable) → refusal — yields two rows so the adapter sees both verdict polarities.

ground_truth is the gold. The dataset has no gold prose answer — only the verdict label. A first run that paired the verdict with a synthesized prose answer scored ~chance (0.52) on the verdict; the synthetic answer was noise. Switching the completion to the gold verdict label ("answerable"/"unanswerable") lifted accuracy to 0.66.

Single-call-per-row simplification

The collator's “last occurrence” marker rule means a conversation with two adapter tool-calls would only supervise the second. For v1, each conversation is truncated at the end of each adapter's answer turn, emitting one row per call — so every adapter call is supervised and the boundary rule stays simple.

7 · What to mask vs. supervise

A training row is one flat text span crossing three rendered turns. The mask boundary falls right after </tool_call>\n:

[M] <|im_start|>assistant\n
[M] <think></think>\n
[M] <tool_call>\n
[M] <function=answerability>\n
[M] <parameter=question>\n
[M] What is our company's parental leave policy for new fathers?\n
[M] </parameter>\n
[M] </function>\n
[M] </tool_call>\n
    >>> MASK BOUNDARY (right after </tool_call>\n) <<<
[S] <|im_start|>user\n
[S] <tool_response>\n
[S] {"answerable": true, "rationale": "…"}\n
[S] </tool_response>\n
[S] <|im_start|>assistant\n
[S] <think></think>Yes. New fathers are eligible for 16 weeks…<|im_end|>
  • Masked (-100): system + tools block, all user turns, and the trigger tool-call turn itself — everything through </function>\n</tool_call>\n.
  • Supervised: the <tool_response> block and the assistant answer turn.

10 · Parsing the generation back into messages

One generate() call produces a stream spanning three logical turns (assistant tool_call → tool_response → final assistant answer), because the single terminal <|im_end|> is the only stop. How an inference engine turns that back into discrete messages depends entirely on the serving stack. Verified on the 4.2 tokenizer: <|im_start|> (id 100256) and <|im_end|> (id 100257) are both single special tokens; the accumulated generation holds 2 embedded <|im_start|> + 1 terminal <|im_end|>.

A — stock server (the trap)

Treats the whole generation as one assistant message: the tool-call parser lifts <tool_call> into tool_calls[], the rest becomes content. The tool_response + answer are stranded in content. With the OpenAI-default skip_special_tokens=True the <|im_start|> markers are deleted on decode, so role boundaries vanish. The 3 messages are not recovered.

B — turn-aware (opt-in)

If the switch runtime decodes with skip_special_tokens=False and splits on <|im_start|>ROLE, it recovers all three cleanly: assistant(tool_call) → user(tool_response) → assistant(answer). Works only because the markers survive — not what a stock endpoint does.

Residual seams even when B succeeds. (1) The tool_response returns under role user (how 4.2 renders tool output), not tool — a downstream re-render could mislabel it. (2) The dropped intermediate <|im_end|> means a strict parser (every <|im_start|> must close before the next opens) sees malformed turns.
Bottom line. The 3-message split is recoverable only if the switch runtime (a) keeps special tokens on decode and (b) deliberately re-segments on <|im_start|>. A naive OpenAI server collapses everything into one assistant message with the tool_response + answer stranded in content, markers stripped. The runtime, not the model, owns this.

What each flow learns

plain one-word verdict

Reads question + docs (injected as a tool message), answers directly with "answerable"/"unanswerable". The completion is one word, so the model fits the format fast and spends its capacity on the decision.

tool verdict + scaffolding

The base emits a <tool_call>; the switch routes to the adapter, which generates the <tool_response> verdict and the answer turn. It must learn the decision and the structural scaffolding, which dilutes the decision signal.

12 · Key takeaways

  1. At this scale the plain flow is both more accurate (0.80 vs 0.66) and more robust (no structural failures, no class bias). Expected: it only learns a 1-word decision; the tool-adapter must also learn the scaffolding.
  2. The adapter-as-tool capability is proven to work — a correctly-trained SR adapter reliably generates the full tool_response + answer at inference under stock generate(). The 12% structural-failure rate and the class bias are scale artifacts (120 rows, 1 epoch), not pipeline defects.
  3. The single-<|im_end|> design is load-bearing. An earlier attempt trained on the fully-stock stream emitted \n<|im_end|> and halted immediately at inference. Dropping the intermediate <|im_end|> took structural validity from 0 → 1.0.
  4. ground_truth is the correct gold. Pairing the verdict with a synthesized prose answer scored ~chance; the gold verdict label lifted accuracy to 0.66.

13 · Open questions & next levers

Next levers (not pipeline changes)

  • Scale: full 3191-row set, multiple epochs, on GPU — both flows should approach the ~0.89 band.
  • Tool-adapter structure robustness: more rows reinforce the two-part structure; alternatively constrain decoding or add a structure-repair step.
  • Class bias: larger / re-balanced data and longer training.

Open questions to resolve

  • Multiple adapters, one model. Each SR adapter is a separate PEFT adapter; serving several means the switch selects by called-function name (or one multi-task adapter). Rows tag metadata.tool_name so they can be split per-adapter later.
  • Does the base ever answer without a tool? Those turns must stay masked — the adapter only owns post-tool-call spans. The one-row-per-call construction handles this automatically.
  • tool_response fidelity. The adapter generates JSON that must parse; eval asserts a valid <tool_response> body with the expected keys before scoring.
  • Verdict↔answer consistency. Train data keeps them consistent; eval checks the answer polarity matches the emitted verdict.
  • Off-spec transcript coherence. Answered in §10: the single-<|im_end|> stream is only re-segmented into messages if the switch runtime keeps special tokens and splits on <|im_start|>; a stock server strands the tool_response + answer in one assistant content.
