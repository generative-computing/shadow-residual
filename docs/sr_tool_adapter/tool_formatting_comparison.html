SR adapter as a tool: two formatting approaches

Granite 4.2-3b. Which part of the chat template the adapter writes, how each variant was scored, and what each scored: answerability in both modes, and three more adapters in external mode (pending).

In both approaches the base model calls an answerability tool and the SR adapter produces the tool's result. They differ in where the adapter takes over and what it writes. At full scale they score the same: 0.95 vs 0.954 verdict accuracy, and 100% valid structure for both.

1 · The two structures

Autoregressive (autoregressive_tool_formatting)

  • The adapter takes over right after the base's </tool_call>.
  • It writes the whole tool-response turn itself, then the opener of the next assistant turn.
  • Its output omits the <|im_end|> separators the stock template would put between those turns.

External (external_tool_formatting)default

  • The serving environment writes the template up to <tool_response>\n.
  • The adapter writes only the verdict dict, then stops on <|im_end|>.
  • The environment closes the tag. The full transcript is byte-identical to the stock 4.2 template.

Autoregressive: what the adapter writes

…<tool_call><function=answerability>…</function>
</tool_call>                                   ← base; adapter takes over here
<|im_start|>user
<tool_response>
{"answerable": true}
</tool_response>
<|im_start|>assistant
"answerable"<|im_end|>                        ← adapter (trained span)

External: what the adapter writes

…</tool_call>                                   ← base
<|im_end|>
<|im_start|>user
<tool_response>                               ← environment; adapter takes over here
{"answerable": true}<|im_end|>                ← adapter (trained span)
</tool_response>
<|im_end|>                                    ← environment closes the turn

2 · How they were trained

Both used the same recipe, so only the formatting differs:

  • Base model: Granite 4.2-3b, ibm-granite/granite-4.2-3b (run on the pre-release checkpoint, which has an identical tokenizer and template).
  • Adapter: SR r32 on q/o and the MLP projections plus cross_stream, thinking off.
  • Compute: 2 epochs (750 optimizer steps) on 4 GPUs (DDP) on Vela.
  • Data: generated inside the job from unified_compare/data_v4, 11,978 training rows and 1,350 held-out rows. The gold verdict is each row's final assistant turn.

3 · How they were evaluated

Both were scored by scripts/eval_tool_adapter.py on the held-out data_v4 rows. Each row's prompt is cut where the adapter takes over. The model then generates freely: greedy decoding, stock generate(), stopping on <|im_end|>. Each output is checked two ways:

  • Structure: does the output parse into a dict with a true/false answerable?
  • Accuracy: does that value match the gold verdict? An output that fails the structure check also counts as wrong.

All three land at 0.94–0.95: wrapping answerability in the tool protocol costs essentially no accuracy.

The held-out losses differ in scale because of what each mode supervises. Autoregressive trains on its whole turn, which is mostly fixed template tokens that are easy to predict. External trains on only the ~7-token dict, where the uncertain verdict token makes up a larger share. The free-generation scores are the comparable numbers.

What changes per adapter

The base calls the tool with the intrinsic's instruction as its argument, taken out of the <guardian> / <requirements> user turn. Its output is what the scorer parses: the dict alone in external mode, or the dict wrapped in the <tool_response> turn in autoregressive mode.

Each row is checked against the stock 4.2 template: with the environment's closing text appended, it is byte-identical (tests/training/test_tool_intrinsics.py). Training: same SR recipe as answerability, 2 epochs, 4 GPUs on Vela, --max-length 12288. Some query-clarification rows reach 11k tokens and would otherwise be cut, losing their labels.

How the tool cells are evaluated

  • Rows: every row of the benchmark's eval set for that intrinsic (adapter-bench/granite-4.2-3b/v1/eval/).
  • Prompt: built by the same code as training. External mode cuts it after <tool_response>\n, autoregressive mode after </tool_call>. Greedy decoding in bf16, stopping on <|im_end|>.
  • Score: the benchmark harness's own scorer and headline metric, run on the dict the adapter wrote. Its code is byte-identical to the harness copy on COS.
  • Runs on Vela: scoring is a separate single-GPU step after training.

6 · Reading the numbers

Tied on accuracy and structure. 0.95 and 0.954 are within one or two errors of each other for these sample sizes. External is the default for its other properties: the adapter learns only the payload, the transcript is stock ChatML, and it stops cleanly on EOS.
Different row counts. The autoregressive score covers the first 500 held-out rows, the external one all 1,350. The autoregressive run's in-job eval hung, and its standalone re-eval was capped at 500 rows. A same-rows comparison would need autoregressive re-scored on all 1,350.
Not the canonical benchmark. The held-out rows come from the same data_v4 source as the training data, and eval_tool_adapter.py scored them. So neither number is comparable to the ~0.89 from the answerability benchmark and its own scorer.
