Shadow Residual — Training & Data Formats

How to train answerability / RAG adapters on Granite 4.1 and Granite 4.2, and how the same data is rendered for each model family.

1. Running training

Training is driven by a single Pydantic-validated YAML. Behavior follows the fields you set — not an architecture name. Reference configs live in src/shadow_residual/config/. The only difference between a 4.1 and a 4.2 run is which config you point at (plus the base-model path); the code auto-adapts to each family's chat format and weight tying.

Pick the config for your model family

Model familyConfigWhat it sets
Granite 4.1 (tied embeddings, role-tag chat format) sr-qo-mlp-r32-c32-sharedkv.yaml base: ibm-granite/granite-4.1-3b; invocation marker <|start_of_role|>assistant<|end_of_role|>
Granite 4.2 (untied lm_head, ChatML format) sr-qo-mlp-r32-c32-sharedkv-g42.yaml base: ${BASE_MODEL} (supply the path); ChatML markers <|im_start|>assistant\n for both invocation_tokens and assistant_marker
The same code handles both. It detects the family from the tokenizer and: respects config.tie_word_embeddings (4.2 ships a separate lm_head.weight); uses the ChatML markers from the 4.2 config for label masking + aLoRA gating; and renders RAG documents the way each family's template expects (see §2). No manual per-model surgery needed.

On the current server

Single GPU:

# Granite 4.1
sr-train \
  --config src/shadow_residual/config/sr-qo-mlp-r32-c32-sharedkv.yaml \
  --train-data /data/train.jsonl \
  --val-data   /data/eval.jsonl \
  --output-dir ./checkpoints

# Granite 4.2 — the config reads model.base from $BASE_MODEL
BASE_MODEL=/path/to/granite-4.2-3b \
sr-train \
  --config src/shadow_residual/config/sr-qo-mlp-r32-c32-sharedkv-g42.yaml \
  --train-data /data/train.jsonl --val-data /data/eval.jsonl \
  --output-dir ./checkpoints

Multi-GPU (DDP for 3b; FSDP for 8b / larger):

# DDP (e.g. 3b on 4 GPUs)
accelerate launch --num_processes 4 --multi_gpu --mixed_precision bf16 \
  -m shadow_residual.training.train --config <cfg>.yaml \
  --train-data /data/train.jsonl --val-data /data/eval.jsonl --output-dir ./ckpt

# FSDP (e.g. 8b on 8 GPUs) — uses the shipped accelerate FSDP config
accelerate launch --config_file src/shadow_residual/config/accelerate/fsdp_4gpu.yaml \
  --num_processes 8 --main_process_port 0 \
  -m shadow_residual.training.train --config <cfg>.yaml \
  --train-data /data/train.jsonl --val-data /data/eval.jsonl --output-dir ./ckpt
FSDP note: the untied-lm_head handling is FSDP-safe — the tie decision is config-driven and settled in the model's __init__ (runs on every rank, incl. meta), so the parameter structure is identical across ranks before the FSDP wrap. Validated end-to-end on both 8b runs.

On Vela

Job YAMLs live in examples/vela/. They clone the repo in-pod, pip install -e ".[train]", then accelerate launch the trainer against COS-mounted data, and finally run the answerability eval. Fill in the token/secret placeholders, then:

oc login --token=… --server=…
helm template -f examples/vela/sr_sharedkv.yaml \
  --set-string "environmentVariables[0].value=$(date -u +%Y%m%dT%H%M%SZ)" \
  mlbatch/pytorchjob-generator | oc create -f -
oc logs -f -c pytorch <jobName>-master-0     # follow

Pin trl<1.7 (already in pyproject) — 1.7 crashes on Granite configs. The Vela image ships torch 2.6 + CUDA 12.4. eval_loss: nan per epoch is expected (prompt-only eval rows have no labels for the trainer's CE); the post-training generation is the real eval.

Evaluation

python -m shadow_residual.eval.answerability_eval --mode peft \
  --base-model <base-model-or-path> \

# --max-new-tokens   (default 30) — enough for 4.2's <think></think>"label" target.

2. Data format & how it renders per model

Training data is JSONL, one chat conversation per row. The last message is the assistant's supervised target; optional documents carry the RAG context. The two model families render that context differently — the code handles the split automatically.

Raw data row INPUT (JSONL)

{
  "messages": [
    { "role": "user",      "content": "What is the capital city of France?" },
    { "role": "assistant", "content": "\"answerable\"" }
  ],
  "documents": [
    { "doc_id": "",
      "text": "The capital city of France is Paris. It is known for its iconic landmarks like the Eiffel Tower, Louvre Museum, and Notre-Dame Cathedral. The city has a population of over 2.2 million people." }
  ]
}

The assistant target here is the literal "answerable" (quoted). documents is passed alongside messages; the code decides how to inject it.

Rendered for Granite 4.1 role-tag format · native documents

<|start_of_role|>system<|end_of_role|>You are a helpful assistant with access to the following documents. You may use one or more documents to assist with the user query.

You are given a list of documents within <documents></documents> XML tags:
<documents>
{"doc_id": "", "text": "The capital city of France is Paris. It is known for its iconic landmarks like the Eiffel Tower, Louvre Museum, and Notre-Dame Cathedral. The city has a population of over 2.2 million people."}
</documents>

Write the response to the user's input by strictly aligning with the facts in the provided documents. If the information needed to answer the question is not available in the documents, inform the user that the question cannot be answered based on the available data.<|end_of_text|>
<|start_of_role|>user<|end_of_role|>What is the capital city of France?<|end_of_text|>
<|start_of_role|>assistant<|end_of_role|>"answerable"<|end_of_text|>

4.1's chat template renders documents= natively into a system turn wrapped in <documents>…</documents>. Role framing is <|start_of_role|>…<|end_of_role|>. The supervised label is the bare "answerable" after the assistant marker.

Rendered for Granite 4.2 ChatML format · documents as tool response

<|im_start|>system
<|im_end|>
<|im_start|>user
What is the capital city of France?<|im_end|>
<|im_start|>user
<tool_response>
[
  {
    "source": "knowledge_base",
    "document_id": "",
    "content": "The capital city of France is Paris. It is known for its iconic landmarks like the Eiffel Tower, Louvre Museum, and Notre-Dame Cathedral. The city has a population of over 2.2 million people."
  }
]
</tool_response>
<|im_end|>
<|im_start|>assistant
<think></think>"answerable"<|im_end|>

4.2's ChatML template ignores the documents= kwarg, so the code injects the documents as an agentic tool response — a tool message rendered as a <tool_response>[…] block (normalized to {source, document_id, content}) after the user turn. The assistant turn carries an empty <think></think> reasoning block before the label.

What differs, side by side

AspectGranite 4.1Granite 4.2
Role framing <|start_of_role|>R<|end_of_role|> <|im_start|>R\n … <|im_end|> (ChatML)
Documents native <documents>…</documents> in a system turn agentic <tool_response>[…]</tool_response> (a tool message)
Assistant target "answerable" <think></think>"answerable"
End-of-turn <|end_of_text|> <|im_end|>
Weight tying tie_word_embeddings=True False (separate trained lm_head.weight)
Both renderings contain the same documents and the same label — only the framing differs. This is why RAG context reaches the model on both families, and why the eval must strip the 4.2 <think></think> prefix before reading the label. The rendering logic lives in src/shadow_residual/training/chat_render.py and is shared by training (data.py) and evaluation (answerability_eval.py) so they stay identical.

3. Handling the thinking / reasoning content

Granite 4.2 (ChatML) can emit a <think>…</think> reasoning block before its answer; Granite 4.1 has no such block. A single boolean — enable_thinking — controls whether that block is requested, and it flows through the same render_chat() helper on both the training and eval paths, so the two never drift. Below is the full lifecycle of thinking content.

3.1 The enable_thinking flag and the reasoning_content key

Two distinct things control thinking, and it helps to keep them apart:

  • enable_thinking carries no reasoning text. On Granite 4.2 it only shapes the trailing generation prompt (appended when add_generation_prompt=True): <think>\n when true (model generates its own reasoning) vs empty <think></think> when false. It does not affect how an already-present assistant message is laid out, and Granite 4.1 ignores it entirely.
  • reasoning_content (a field on the assistant message) is the only supported way to supply reasoning text on 4.2. If non-empty, the template wraps it as <think>\n{reasoning_content}\n</think>\n{content} — you provide plain text, the template adds the tags. Inlining <think>…</think> in content does not work: the generation prompt appends its own <think> opener, so a model trained that way emits a second block — you get two <think> sections.

The flag's value is forwarded through the shared render_chat() helper on both paths:

PathSource of enable_thinking (default False)
Training data.enable_thinking in the YAML, overridable by --thinking on sr-train (CLI wins).
Evaluation --enable-thinking flag on answerability_eval.
SR's loader passes messages through verbatim — it does not populate reasoning_content, so that key only takes effect if your JSONL rows already carry it. And keep training and eval in agreement: thinking is a prompt-rendering choice, so flip enable_thinking on for both sides or neither. The reference answerability adapters are trained thinking-off and evaluated without --enable-thinking.

3.2 Thinking in the training target

When thinking is off (the default), Granite 4.2's assistant turn still carries an empty reasoning block — the template emits <think></think> immediately before the label:

<|im_start|>assistant
<think></think>"answerable"<|im_end|>

The supervised label is the bare "answerable" that follows the empty tags (the <think></think> pair is part of the unmasked assistant turn the model is trained to reproduce). Granite 4.1 has no reasoning block, so its target is just "answerable". Response-only masking is unaffected either way: loss is computed on the final assistant turn regardless of whether it opens with an empty think block.

3.3 Thinking in generated output — the eval parser

At generation time a 4.2 model produces whatever the template shaped it for. If a non-empty reasoning block appears, the classifier must not mistake the reasoning prose for the label. process_predictions() in answerability_eval.py handles this by reading only the text after the last </think>:

pred = pred.strip()
# 4.2: the verdict is whatever follows the last </think>.
if "</think>" in pred:
    pred = pred.rsplit("</think>", 1)[1].strip()
# ... then take the first token / quoted word as the label
  • With a think block (e.g. <think>Okay, the user is asking…</think>"unanswerable") → everything up to and including </think> is discarded; the label is parsed from the remainder.
  • With an empty block (<think></think>"answerable") → the split leaves "answerable", parsed as normal.
  • No block at all (Granite 4.1) → the </think> branch is skipped; parsing is unchanged.
Set --max-new-tokens large enough to cover the reasoning block plus the label when thinking is on. The default (30) is sized for the thinking-off <think></think>"label" target; a real reasoning trace needs more room or it will be truncated before the label is emitted.
